# Step 7: Driver/Reason Analysis Audit

## A. Where Step 6 output is created
Step 6 is implemented via the `backend/opportunity_engine.py` and the `POST /v1/navigation-opportunity` endpoint. It creates the `navigation_opportunity_score` and `navigation_opportunity_level`.

## B. Where opportunity_session_id is stored
It is stored in the `opportunity_sessions` table in `backend_state.sqlite`.

## C. Where Step 6 evidence is generated
The evidence object is generated deterministically in `backend/opportunity_engine.py` and saved as a JSON string in the `opportunity_sessions` table.

## D. Whether drivers are already generated
Yes, drivers are currently generated in two places:
1. `project_scripts/build_kg_rag.py` generates basic string drivers and stores them in the Knowledge Graph (`evidence_graph.sqlite`).
2. `backend/opportunity_engine.py` generates a simple string array of drivers (e.g., `["LOW_OUTPATIENT_UTILIZATION"]`) and stores them in `opportunity_sessions`.
However, neither produces the required structured JSON driver objects with confidence levels and numerical evidence.

## E. Whether drivers are deterministic or LLM-generated
Current drivers are deterministic (rule-based if/else statements). They are not generated by an LLM.

## F. Whether drivers are based on real member data
Yes, they use the `ed_visits_90d`, `outpatient_visits_90d`, etc., generated point-in-time from the CMS claims pipeline.

## G. Whether the Knowledge Graph is actually used
Yes, `backend/main.py` uses `kg_case()` to fetch the raw `attributes_json` and `drivers` edges from `evidence_graph.sqlite`.

## H. Whether RAG is actually used
RAG documents exist in `kg_rag/knowledge_base/` but they are not dynamically generating the driver logic. The driver logic is hardcoded in python prior to insertion into the DB.

## I. Whether the existing pathway engine consumes drivers
Yes, `/v1/pathways` currently checks for `"LOW_OUTPATIENT_UTILIZATION" in opp_drivers` to route to `CARE_MANAGEMENT`.

## J. Whether any driver can be hallucinated
No. Because the generation is strictly deterministic code, it cannot hallucinate. However, missing data (like PCP relationships) is implicitly assumed in some systems, which we protected against in Step 6 by marking `DATA_UNAVAILABLE`.
